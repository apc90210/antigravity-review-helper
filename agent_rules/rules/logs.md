Обязательное правило работы с проектом: ведение протокола изменений

Ты работаешь внутри проекта и обязан вести единый протокол изменений.

Ты обязан использовать журнал изменений проекта (logs/YYYY-MM-DD.md с текущей датой) как основной источник контекста текущей работы.

1. Общие требования
Перед началом любых изменений проверь наличие каталога logs в корне проекта.
Если каталога logs нет — создай его.
Для текущего рабочего дня создай файл журнала с именем в формате:
logs/YYYY-MM-DD.md

Пример для текущей даты:

logs/2026-04-23.md
Если файл за текущую дату уже существует — не создавай новый, а продолжай писать в него.
Все записи вноси последовательно, без удаления старых записей.
Новые записи всегда добавляй в конец файла.
Журнал должен вестись на протяжении всего проекта, при каждом изменении.
2. Когда делать запись в журнал

Ты обязан делать запись:

перед началом значимого блока работ;
после каждого изменения файлов;
после создания новых файлов;
после удаления файлов;
после изменения структуры БД;
после изменения API;
после изменения логики моделей, фич, пайплайнов, экспорта;
после исправления ошибок;
после завершения задачи.

Если изменений несколько, фиксируй их в порядке выполнения.

3. Формат записи

Каждая новая запись должна оформляться так:

## HH:MM

### Задача
Кратко опиши, какую задачу выполнял.

### Изменения
- файл / модуль / таблица
- что именно изменено
- зачем изменено

### Детали
- перечисли ключевые технические решения
- укажи новые зависимости, миграции, маршруты, таблицы, поля, сервисы, функции

### Статус
- done / partial / failed

### Следующий шаг
Кратко укажи, что нужно делать дальше.
4. Обязательные правила заполнения
Пиши конкретно, без общих фраз.
Всегда указывай точные пути файлов.
Если менялась БД — указывай:
схему
таблицу
новые поля / индексы / ограничения
Если менялся backend — указывай:
модуль
endpoint
сервис
Если менялась модельная логика — указывай:
какая модель
какие фичи
какой pipeline step
Если вносились миграции — обязательно укажи имя migration-файла.
Если ничего не удалось завершить — это тоже фиксируй в журнале.
5. Формат для первой записи за день

Если файл за день создается впервые, начни его так:

# Журнал изменений за YYYY-MM-DD

## HH:MM

### Задача
Инициализация журнала изменений за текущий день.

### Изменения
- Создан ежедневный файл протокола изменений.

### Детали
- Все последующие изменения за день должны добавляться последовательно в этот файл.
- Формат ведения журнала стандартизирован для всех агентов проекта.

### Статус
- done

### Следующий шаг
- Продолжить фиксацию всех изменений по мере работы.
6. Запреты
Не перезаписывай старые записи.
Не создавай несколько журналов на один день без необходимости.
Не пропускай изменения.
Не объединяй задним числом разные изменения в одну размытую запись.
Не пиши “внесены правки” без перечисления, что именно изменено.
7. Приоритет

Это правило является обязательным для всех агентов и применяется ко всем задачам в проекте без исключения.

Перед любыми изменениями:

проверь logs/YYYY-MM-DD.md
создай файл при отсутствии
после каждого шага обновляй журнал
